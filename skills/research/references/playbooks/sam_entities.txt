======================================================================
DATA MODEL AWARENESS
======================================================================

Important facts about this dataset:

1. `sam_entities.data` contains the flattened full entity record.
2. Repeating sections are also split into separate tables:
   - business_types
   - geographic_areas_served
   - naics
   - psc
   - sba_business_types
3. All fields are stored as strings.
4. Even dates, flags, numeric-looking values, codes, and counts are strings unless explicitly cast in SQL.
5. NULL-like values may appear as:
   - NULL
   - empty string ''
   - string literals such as 'null'
   - display placeholders such as 'ᴺᵁᴸᴸ'
6. Boolean-like values are often stored as strings such as:
   - 'Y' / 'N'
   - 'YES' / 'NO'
   - 'Yes' / 'No'
   - 'Active' / 'Inactive'

You must write SQL accordingly.

SQL GENERATION RULES
======================================================================

1. Always use explicit column names whenever possible.
   Avoid SELECT * unless the user explicitly wants all fields.

2. Always map user language to actual schema fields.

Examples:
- "UEI" -> entityData__entityRegistration__ueiSAM
- "CAGE" -> entityData__entityRegistration__cageCode
- "legal business name" -> entityData__entityRegistration__legalBusinessName
- "status" -> entityData__entityRegistration__registrationStatus
- "expiration date" -> entityData__entityRegistration__registrationExpirationDate
- "physical city" -> entityData__coreData__physicalAddress__city
- "state" -> prefer readable state field if available
- "entity type" -> entityData__coreData__generalInformation__entityTypeDesc
- "business type" -> split table if requested, otherwise full table field if available
- "NAICS" -> split table if requested, otherwise main-table assertions field if available
- "PSC" -> split table if requested, otherwise main-table assertions field if available

3. Prefer the most semantically direct field.

4. Prefer readable description fields when the user wants business-facing output.
   Prefer code fields when the user explicitly asks for codes.

5. For counts, use count().
   For distinct entities, use countDistinct() or uniq().

6. For date analysis, parse date strings first.

7. For top lists:
   - aggregate first
   - order descending
   - apply LIMIT

8. For text search:
   - use ILIKE when case-insensitive matching is appropriate
   - clean obvious null placeholders if needed

9. For null handling:
   - treat '', 'null', 'NULL', and 'ᴺᵁᴸᴸ' as missing when needed

10. When filtering on date ranges, parse the string date first.

Example:
WHERE parseDateTimeBestEffortOrNull(entityData__entityRegistration__registrationDate) >= toDate('2026-01-01')
  AND parseDateTimeBestEffortOrNull(entityData__entityRegistration__registrationDate) < toDate('2027-01-01')

11. Keep aliases clean and readable.

12. Never reference columns not present in the approved schema.
